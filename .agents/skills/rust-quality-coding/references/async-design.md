# Async、并发与服务边界

async 的价值是让等待 I/O 的任务互不堵塞，不是把每个函数都改成 `async fn`。先画出任务、资源和消息的关系，再选 runtime、锁和 channel。项目已有运行时与框架时，优先遵循其约定；新引入 Tokio、Axum 或其他运行时属于架构决策。

## 划出 async 边界

让网络、文件、数据库、timer 和外部 RPC 等等待点位于 async 调用链中。领域计算、验证、格式化和纯数据转换保持同步，除非它们本身要等待。长时间 CPU 计算或无法替换的阻塞库不能直接占用 async worker；将它们移到运行时提供的 blocking executor 或专用线程，并让调用者能处理执行结果。

`spawn` 表示独立生命周期：task 可能比创建它的栈帧活得久。把 task 所需的拥有值移进去，或 clone 一个明确的共享句柄；不要让 task 借用局部变量。若 task 的结果、错误或退出时机重要，就保留并 await `JoinHandle`；丢弃 handle 不是取消策略。

## 共享状态前先选择所有权模型

| 状态关系 | 首选设计 |
| --- | --- |
| 一个 task 可以独占状态，其他人发请求 | task 持有状态，使用 channel 传命令和回复 |
| 多 task 只读同一份数据 | `Arc<T>` |
| 多 task 短暂读写同一对象 | `Arc<Mutex<T>>` 或 `Arc<RwLock<T>>`，按访问模式选锁 |
| 简单计数或标志 | 合适的原子类型，并说明所需内存序 |

锁只能保护一个清晰的不变量。持锁区间内完成必须原子完成的读、校验和写，然后释放 guard，再执行网络、sleep、channel 等待或重计算。异步 mutex 可以技术上跨 `.await`，但这会串行化其他使用者并放大死锁与延迟风险；只有设计明确要求时才这样做。同步 mutex 在 async 代码中并非一律错误，但它必须非常短，且 guard 绝不能跨 `.await`。

## Channel 表达拓扑与背压

选择 channel 应由消息如何流动决定：

| 关系 | 常见选择 |
| --- | --- |
| 多生产者，一个处理者 | `mpsc` |
| 一次请求，一次回复 | `oneshot`，常作为 mpsc 消息的一部分 |
| 每个订阅者都应看到事件 | `broadcast` |
| 消费者只关心当前最新值 | `watch` |

队列容量是产品语义的一部分：有界队列把生产过快变成可等待或可拒绝的背压；无界队列把风险变成内存增长。为关闭定义协议：谁停止发送、谁丢弃 sender、谁处理 `recv() == None` 和发送失败。并发等待所有任务时用 join/收集 handles；只要第一个完成或多个事件中任意一个时用 `select!`，并明确其余工作是否取消、继续还是需要清理。

## 网络和协议

TCP 是字节流，不提供消息边界。协议层必须定义长度前缀、分隔符、固定长度或其他 framing；业务 handler 接收完整消息，而不是猜测一次 `read` 是否恰好读全。收到 EOF 表示对端关闭写端，应走连接关闭逻辑。

解析结构化文本或二进制时，先把输入、剩余输入、成功值和错误类型写进小 parser 的签名，再组合它们。是否选 nom、手写 parser 或 serde 取决于协议和已有依赖；关键是解析失败不能悄悄变成默认业务值，并且各层都有可测的边界。

## HTTP 服务中的边界

以 Axum 为例，router 把 URL 和中间件组织成模块；handler 负责提取 HTTP 输入、调用领域服务并转换响应。请求 DTO、领域模型和存储记录可相同，也可不同；当它们的校验、字段暴露或演进速度不同，就应分开。

- body 只能消费一次，因此会读取 body 的 extractor（如 `Json`）需要放在其他 extractor 之后。
- `AppState` 持有明确共享的依赖，例如连接池和配置，并通过框架 state 注入。避免 handler 隐式读取可变全局。
- 统一错误响应时，为领域错误实现到 HTTP 响应的映射；不要在每个 handler 里复制 `match` 或 `unwrap`。
- 使用项目已有的结构化日志与 request tracing。日志记录边界事件、失败上下文和相关标识，避免把敏感输入当调试文本输出。

服务代码的可维护性来自边界清楚：transport 处理协议，应用层协调用例，领域层维护不变量，基础设施实现 I/O。它们不必为形式上的分层创建空壳模块，但不应让 HTTP、SQL 或 runtime 细节渗入所有业务类型。
